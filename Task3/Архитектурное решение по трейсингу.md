# Архитектурное решение по трейсингу

## 1. Анализ системы в контексте трейсинга

### Системы, которые следует покрыть трейсингом

На C4-диаграмме выделены следующие компоненты, через которые проходит заказ:

1. **Shop API** (SpringBoot) — создание заказа, загрузка 3D-файла, отправка в очередь
2. **RabbitMQ** — передача сообщений между Shop API → MES API и MES API → CRM API
3. **MES API** (C#) — расчёт стоимости, назначение на оператора, изменение статусов производства
4. **CRM API** (SpringBoot) — подтверждение заказа, закрытие заказа
5. **3D files storage** (S3) — загрузка и чтение 3D-файлов
6. **Shop DB** (PostgreSQL) — запись/чтение данных о заказах
7. **MES DB** (PostgreSQL) — запись/чтение данных о производстве

### Места, где заказ может «сломаться» или зависнуть

| Место | Описание проблемы | Критичность |
|-------|-------------------|-------------|
| **Shop API → RabbitMQ** | Сообщение о новом заказе (SUBMITTED) не доставлено в очередь. MES никогда не узнает о заказе. | Критическая |
| **RabbitMQ → MES API** | Потребитель MES не обработал сообщение (crash, timeout, nack без retry). Заказ остаётся в SUBMITTED навсегда. | Критическая |
| **MES API — расчёт стоимости** | Расчёт занимает 2-30 минут. Может зависнуть, упасть по OOM, потерять результат. Заказ застрянет в SUBMITTED → PRICE_CALCULATED. | Высокая |
| **MES API → RabbitMQ** | Сообщение об изменении статуса (PRICE_CALCULATED, MANUFACTURING_COMPLETED и т.д.) не доставлено в CRM. | Критическая |
| **RabbitMQ → CRM API** | CRM не обработала сообщение. Заказ не подтверждён (MANUFACTURING_APPROVED не выставлен). | Высокая |
| **MES API (B2B вход)** | API-партнёр отправил заказ, но MES API не обработал его корректно. Партнёр не получает обратную связь. | Высокая |
| **Shop API → S3** | Загрузка 3D-файла не завершилась. Заказ в статусе FILE_UPLOADED, но файла нет. | Средняя |

### Данные, которые должны попадать в трейсинг

Каждый span должен содержать:

**Обязательные атрибуты:**
- `order.id` — идентификатор заказа (главный ключ для поиска)
- `order.status` — текущий статус заказа на момент операции
- `service.name` — имя сервиса (shop-api, crm-api, mes-api)
- `operation.name` — имя операции (create-order, calculate-price, approve-manufacturing)

**Контекстные атрибуты:**
- `customer.id` — идентификатор клиента (для поиска по клиенту)
- `order.source` — источник заказа (b2c-web, b2b-api, b2b-partner-id)
- `order.status_from` / `order.status_to` — переход статуса
- `calculation.duration_ms` — время расчёта стоимости
- `calculation.polygon_count` — сложность 3D-модели
- `queue.name` — имя очереди RabbitMQ
- `message.id` — идентификатор сообщения в RabbitMQ
- `error.type` / `error.message` — информация об ошибке (если произошла)
- `db.statement` — тип запроса к БД (без чувствительных данных)

## 2. Мотивация

### Почему трейсинг необходим

Компания теряет заказы и контракты. Заказ проходит через три системы (Shop → MES → CRM) и брокер сообщений. Без end-to-end трейсинга невозможно ответить на простой вопрос: «Где сейчас заказ #12345 и что с ним случилось?»

Текущий способ диагностики — расспросить клиента, вручную проверить каждую базу данных, прочитать логи на каждом сервере. Это занимает часы или дни.

### Технические и бизнес-метрики, на которые повлияет внедрение

1. **MTTR (Mean Time To Recovery)** — время обнаружения и устранения проблем с заказами сократится с дней до минут. Трейс покажет, где именно заказ застрял.

2. **Процент «потерянных» заказов** — впервые можно будет измерить реальный масштаб проблемы. Предположительно — значительный процент заказов не доходит до PRICE_CALCULATED.

3. **Среднее время выполнения заказа (lead time)** — трейсинг покажет, сколько времени заказ проводит на каждом этапе, и где bottleneck.

4. **Удовлетворённость B2B-партнёров** — возможность предоставить партнёрам статус заказа в реальном времени вместо «мы разбираемся».

5. **Эффективность очередей RabbitMQ** — визуализация задержек между публикацией и потреблением сообщений покажет проблемы с доставкой.

## 3. Предлагаемое решение

### Технологический стек

- **OpenTelemetry SDK** — единый стандарт инструментирования для всех языков (Java, C#, JavaScript).
- **Jaeger** — backend для хранения и визуализации трейсов. Open-source, хорошо интегрируется с OpenTelemetry.
- **OpenTelemetry Collector** — промежуточный компонент для приёма, обработки и экспорта телеметрии.

### Почему именно этот стек

- OpenTelemetry — вендор-нейтральный стандарт, поддерживает Java (Spring Boot), C# (.NET) и JavaScript.
- Jaeger — зрелый open-source проект, поддерживает поиск по trace ID и по атрибутам (order.id).
- Collector позволяет централизовать обработку и снижает нагрузку на приложения.

### Компоненты для внедрения

#### Новые компоненты (выделены красным на схеме)

1. **OpenTelemetry Collector** — центральный компонент сбора телеметрии.
   - Принимает трейсы от всех сервисов по OTLP (gRPC/HTTP).
   - Экспортирует в Jaeger.
   - Развёртывается как отдельный сервис (EC2 или контейнер).

2. **Jaeger** (all-in-one или collector + query + storage).
   - Хранение трейсов в Elasticsearch или Cassandra (для production) или в памяти (для dev).
   - Jaeger Query — UI для поиска и визуализации трейсов.
   - Развёртывается как отдельный сервис.

#### Доработки существующих компонентов

3. **Shop API** — добавить OpenTelemetry Java SDK:
   - Auto-instrumentation для Spring Boot (HTTP, JDBC, RabbitMQ).
   - Кастомные спаны: создание заказа, загрузка файла, публикация в очередь.
   - Добавление атрибутов order.id, customer.id, order.status.

4. **CRM API** — добавить OpenTelemetry Java SDK:
   - Auto-instrumentation для Spring Boot (HTTP, JDBC, RabbitMQ).
   - Кастомные спаны: подтверждение заказа, закрытие заказа.
   - Извлечение trace context из сообщений RabbitMQ.

5. **MES API** — добавить OpenTelemetry .NET SDK:
   - Auto-instrumentation для ASP.NET (HTTP, ADO.NET).
   - Кастомные спаны: расчёт стоимости, назначение на оператора, изменение статуса.
   - Инжекция/извлечение trace context в/из RabbitMQ-сообщений.

6. **RabbitMQ** — пропагация trace context:
   - При публикации сообщения — trace context сериализуется в headers сообщения.
   - При потреблении — trace context извлекается из headers и продолжает трейс.
   - Это ключевой момент: без пропагации через RabbitMQ трейс будет разорван на три части.

## 4. Компромиссы

### Где трейсинг не принесёт пользы или обойдётся дорого

1. **Фронтенд-приложения (Internet Shop, CRM, MES SPA).** Трейсинг браузерного JavaScript возможен через OpenTelemetry JS SDK, но:
   - Увеличивает размер бандла и нагрузку на браузер пользователя.
   - Данные отправляются с клиента — ненадёжный канал.
   - На первом этапе достаточно трейсить бэкенды. Фронтенд-трейсинг — на будущее.

2. **S3-хранилище.** S3 — managed-сервис, инструментировать его изнутри невозможно. Можно трейсить вызовы к S3 со стороны Shop API и MES API (и это нужно делать), но задержки внутри S3 останутся «чёрным ящиком».

3. **Расчёт стоимости (внутренняя логика MES).** Если MES был куплен с исходным кодом, но код сложный и плохо документирован, глубокое инструментирование алгоритма расчёта может быть слишком дорогим. Компромисс: трейсить на уровне «вход → выход» (начало расчёта, конец расчёта, результат), без инструментирования внутренних шагов алгоритма.

4. **Managed-сервисы баз данных.** PostgreSQL как Managed Service не позволяет устанавливать агенты внутрь. Трейсим запросы со стороны приложения (через JDBC/ADO.NET instrumentation), но internal DB latency (locks, vacuum, replication) — через метрики, а не трейсы.

5. **Overhead на production.** Трейсинг добавляет ~1-5% overhead на каждый запрос. Для системы с проблемами производительности (MES) это нужно учитывать. Решение: sampling — не трейсить 100% запросов, а например 10-50% для production.

## 5. Аспекты безопасности

### Несанкционированный доступ

1. **Аутентификация Jaeger UI:**
   - Jaeger UI доступен только из внутренней сети компании (VPN/VPC).
   - Reverse proxy (nginx) перед Jaeger Query с аутентификацией через корпоративный SSO.
   - Доступ имеют: разработчики, DevOps, техлид, PM (роль «Поддержка»).
   - Операторы и продавцы не имеют доступа к Jaeger.

2. **OpenTelemetry Collector:**
   - Принимает данные только от известных сервисов внутри VPC.
   - OTLP-эндпоинт не выставлен наружу.
   - mTLS между сервисами и Collector (рекомендуется для production).

3. **Сеть:**
   - Jaeger, Collector и хранилище трейсов размещены в приватной подсети.
   - Доступ к Jaeger UI только через VPN или bastion host.
   - Security Groups ограничивают доступ к портам Collector (4317, 4318) и Jaeger (16686).

### Чувствительные данные в трейсах

4. **Не логировать PII (Personally Identifiable Information):**
   - В атрибуты span НЕ попадают: ФИО, email, телефон, адрес доставки, платёжные данные.
   - Используем только идентификаторы: customer.id, order.id, partner.id.
   - В OTel Collector настроить процессор `attributes` для фильтрации чувствительных полей.

5. **Ротация и retention:**
   - Трейсы хранятся 14 дней (достаточно для расследования инцидентов).
   - Автоматическое удаление по TTL.

## 6. Автоматический мониторинг и алертинг на основе данных трейсинга (дополнительное задание)

### Идея

Данные трейсинга содержат информацию о каждом переходе заказа между статусами. Из них можно автоматически:
- Обнаруживать «зависшие» заказы (нет следующего span дольше порогового времени).
- Измерять SLI/SLO для каждого этапа заказа.
- Алертить при деградации.

### Реализация

1. **Jaeger SPM (Service Performance Monitoring)** — встроенная функция Jaeger, которая агрегирует данные трейсов в метрики (RED-метрики per service + per operation).

2. **Prometheus + OTel Collector Spanmetrics Connector:**
   - OTel Collector может генерировать метрики из трейсов (spanmetrics connector).
   - Метрики экспортируются в Prometheus.
   - В Grafana строятся дашборды и алерты.

3. **Алерты на зависшие заказы:**
   - Метрика: `order_status_transition_duration_seconds{from="SUBMITTED", to="PRICE_CALCULATED"}`
   - Алерт: если p99 > 60 минут ИЛИ count упал до 0 (заказы перестали переходить).

4. **Алерт на рост ошибок в пути заказа:**
   - Метрика: `traces_spanmetrics_calls_total{status_code="ERROR", service_name="mes-api"}`
   - Алерт: error rate > 5% за 5 минут.
