# Планирование: анализ, идентификация проблем и поиск решений

## 1. Описание текущей системы

Компания «Александрит» — производитель ювелирных украшений (готовых и на заказ). Пользователь может загрузить собственную 3D-модель или создать её в конструкторе на сайте. Система состоит из трёх приложений:

- **Онлайн-магазин** — Vue + Java Spring Boot. Работа с клиентами B2C: каталог, загрузка 3D-моделей, оформление заказов.
- **CRM** — Vue + Java Spring Boot. Работа продавцов с заказами, подтверждение производства.
- **MES** — React + C#. Управление производством: расчёт стоимости, назначение заказов на операторов, отслеживание статусов.

Интеграция MES <-> CRM идёт через RabbitMQ. Все приложения работают на единичных EC2-инстансах в Yandex Cloud. Базы данных — Managed PostgreSQL (по одному инстансу на чтение+запись). Хранилище 3D-файлов — S3.

### Статусы заказа

```
INITIATED → FILE_UPLOADED → SUBMITTED → PRICE_CALCULATED → MANUFACTURING_APPROVED →
→ MANUFACTURING_STARTED → MANUFACTURING_COMPLETED → PACKAGING → SHIPPED → CLOSED
```

Системы-владельцы переходов:
- Онлайн-магазин: INITIATED, FILE_UPLOADED, SUBMITTED
- MES: PRICE_CALCULATED, MANUFACTURING_STARTED, MANUFACTURING_COMPLETED, PACKAGING, SHIPPED
- CRM: MANUFACTURING_APPROVED, CLOSED

**Важный нюанс: два flow создания заказа.**

1. **B2C flow:** заказ создаётся в онлайн-магазине (INITIATED → FILE_UPLOADED → SUBMITTED), затем MES через API магазина получает 3D-модель и считает стоимость (PRICE_CALCULATED), после чего событие уходит в CRM через RabbitMQ.
2. **B2B flow (через открытый API):** внешний партнёр обращается к API «Александрита», MES считает стоимость и **сам инициирует создание заказа в CRM через сообщение в RabbitMQ** (см. company.md, описание проблем). То есть для B2B-заказов CRM узнаёт о заказе только из очереди — если сообщение потерялось, заказа для продавца не существует.

Этот нюанс критичен для анализа P1: у B2B-заказов нет «страховки» в виде записи в онлайн-магазине.

## 2. Идентифицированные проблемы

### P1. Потеря и зависание заказов (критическая)

**Симптомы:** клиенты B2C и API-партнёры жалуются на не полученные заказы; заказы висят месяцами вместо обещанных трёх недель. Жалобы усилились после открытия B2B API.

**Гипотезы о корневых причинах** (требуют верификации после внедрения observability — И1):
- Сообщения теряются или застревают в RabbitMQ между MES и CRM. Отсутствуют Dead Letter Queue (DLQ), publisher confirms, consumer ack, retry-политики — любой сбой consumer'а или кратковременная недоступность брокера может приводить к молчаливой потере сообщений.
- Для B2B-заказов потеря сообщения из MES → CRM означает, что заказ не появляется у продавца вообще (см. раздел 1, B2B flow).
- Отсутствие трейсинга — невозможно определить, на каком этапе заказ «застрял».
- Нет алертинга на «зависшие» заказы (например, заказ в статусе SUBMITTED более 30 минут).

**Почему это гипотезы, а не факты:** без метрик RabbitMQ и distributed tracing мы не можем доказать, где именно теряются заказы. Это ещё один аргумент в пользу приоритета И1 (observability) — она должна идти первой, чтобы подтвердить или опровергнуть предположения.

### P2. Медленная работа MES — дашборд заказов (высокая)

**Симптомы:** первая страница MES (список заказов по статусам) грузится долго. Пагинация и фильтры не помогли.

**Корневые причины:**
- Один инстанс MES DB обслуживает и чтение дашборда, и запись (расчёт цены, обновление статусов). При росте нагрузки чтение и запись конкурируют.
- Расчёт стоимости — тяжёлая операция (2-30 минут), которая нагружает MES API и потенциально блокирует БД.
- Нет кеширования данных дашборда — каждый запрос оператора выполняет полный запрос к БД.
- Нет индексов или они неоптимальны для сортировки «самые новые заказы первыми».

### P3. Единая точка отказа (Single Point of Failure) (высокая)

**Симптомы:** любой сбой одного инстанса полностью останавливает соответствующий сервис.

**Корневые причины:**
- По одному EC2-инстансу на приложение — нет горизонтального масштабирования.
- По одному инстансу БД — нет реплик чтения.
- Один инстанс RabbitMQ (подразумевается) — потеря брокера останавливает всю интеграцию.

### P4. Отсутствие observability (высокая)

**Симптомы:** проблемы обнаруживаются по жалобам клиентов; разбор инцидентов идёт «со слов клиента»; невозможно оценить реальное здоровье системы.

**Корневые причины:**
- Нет мониторинга инфраструктуры и приложений.
- Нет distributed tracing — невозможно проследить путь заказа через три системы.
- Нет централизованного логирования — разработчики читают логи вручную на каждом сервере.

### P5. Общая база данных Shop DB для Shop API и CRM API (средняя)

**Симптомы:** потенциальное узкое место при росте нагрузки.

**Корневые причины:**
- Shop API и CRM API работают с одной и той же PostgreSQL. При росте числа заказов конкуренция за соединения и блокировки будут расти.
- Изменение схемы для нужд одного приложения может сломать другое.

### P6. Медленный и нестабильный релизный цикл (средняя)

**Симптомы:** задержки релизов растут, раньше не превышали месяц — теперь дольше.

**Корневые причины:**
- Ручное E2E-тестирование — единственный QA вручную прогоняет сценарии.
- Ручной деплой в release и prod — человеческий фактор.
- Нет автоматизированных тестов, кроме юнит-тестов.

### P7. API для B2B-партнёров не имеет rate limiting и отдельного SLA (низкая)

**Симптомы:** после открытия API компанию «завалило заказами», количество жалоб выросло.

**Корневые причины:**
- API-партнёры отправляют заказы напрямую в MES API — нет квот, нет приоритизации, нет отдельного контроля нагрузки.
- Всплеск заказов от B2B «топит» и B2C-клиентов — общие ресурсы.

## 3. Инициативы для устранения проблем

### И1. Внедрение observability-стека (мониторинг + трейсинг + логирование)

**Решает:** P4, частично P1, P2
**Описание:**
- Мониторинг: Prometheus + Grafana для метрик инфраструктуры и приложений.
- Трейсинг: OpenTelemetry SDK во все сервисы + Jaeger для визуализации пути заказа.
- Логирование: ELK/OpenSearch для централизованного сбора и анализа логов.
- Алертинг на зависшие заказы, рост ошибок, деградацию latency.

### И2. Надёжная доставка сообщений в RabbitMQ

**Решает:** P1
**Описание:**
- Настроить Dead Letter Queue (DLQ) для всех очередей.
- Внедрить publisher confirms и consumer acknowledgements.
- Добавить retry-политики с экспоненциальным backoff.
- Мониторинг DLQ и in-flight сообщений через Prometheus-exporter RabbitMQ.
- Кластеризация RabbitMQ (минимум 3 ноды) для отказоустойчивости.

### И3. Кеширование дашборда MES

**Решает:** P2
**Описание:**
- Внедрить Redis как серверный кеш для списка заказов на дашборде.
- Паттерн Cache-Aside: при чтении — проверяем кеш, при промахе — идём в БД.
- Инвалидация при изменении статуса заказа (event-driven через RabbitMQ).
- Добавить read-реплику MES DB для разделения нагрузки чтения и записи.

### И4. Горизонтальное масштабирование и контейнеризация

**Решает:** P3
**Описание:**
- Контейнеризация всех приложений (Docker).
- Миграция в Kubernetes для автоскейлинга и self-healing.
- Минимум 2 реплики каждого сервиса.
- Read-реплики для БД.
- Выделить расчёт стоимости в отдельные воркеры (горизонтально масштабируемые).

### И5. Автоматизация тестирования и CI/CD

**Решает:** P6
**Описание:**
- Написать E2E-автотесты для критических сценариев (создание заказа, расчёт стоимости, смена статусов).
- Автоматический запуск тестов в CI-пайплайне.
- Автоматический деплой в release/prod после прохождения тестов (с manual approval gate для prod).
- QA-инженер переходит от ручного тестирования к автоматизации (он уже хочет этим заняться).

### И6. Разделение API для B2B и B2C + rate limiting

**Решает:** P7, частично P1
**Описание:**
- API Gateway перед MES API с rate limiting для B2B-партнёров.
- Отдельные квоты и SLA для B2B и B2C.
- Приоритизация запросов — B2C-заказы не должны страдать от всплеска B2B.

### И7. Разделение Shop DB (стратегическая, долгосрочная)

**Решает:** P5
**Описание:**
- Выделить данные CRM в отдельную БД.
- Синхронизация через события (Event-Driven Architecture) или CDC (Change Data Capture).
- Это устраняет связанность Shop API и CRM API на уровне данных.

### Локальные («быстрые») задачи

Помимо эпиков — набор точечных задач, которые можно сделать за часы/дни и получить заметный эффект:

- **Л1. Индексы в MES DB** для сортировки и фильтрации дашборда по `(status, created_at DESC)`. Решает часть P2 за несколько часов работы DBA, до внедрения кеша.
- **Л2. Алерт «заказ завис»** — простой cron-скрипт + Telegram/Slack webhook, который раз в 10 минут ищет заказы в нетерминальных статусах дольше SLA (например, SUBMITTED > 30 мин, PRICE_CALCULATED > 2 ч). Даёт проактивную видимость P1 ещё до полноценного observability-стека.
- **Л3. Nginx rate limiting для B2B API** — временная мера до полноценного API Gateway (И6). Одна конфигурация nginx, защищает B2C от всплесков B2B.
- **Л4. Ручной аудит RabbitMQ** — проверить текущие настройки (durable queues, publisher confirms, prefetch, ack mode), составить чек-лист проблем. Задача на 1–2 дня, часто выявляет очевидные дыры без внедрения большого решения.
- **Л5. Health-check эндпоинты** во всех трёх приложениях + простой uptime-мониторинг (UptimeRobot или аналог). Даёт базовую видимость доступности за день работы.

Эти задачи хороши тем, что их можно делать параллельно с эпиками, они дают «быстрые победы» и снимают часть боли, пока идёт работа над И1–И7.

## 4. Приоритизация инициатив

### Критерии приоритизации

1. **Влияние на бизнес** — теряем клиентов и контракты прямо сейчас?
2. **Срочность** — проблема усугубляется с ростом нагрузки?
3. **Сложность реализации** — сколько усилий и людей потребуется?
4. **Зависимости** — нужно ли это сделать до других инициатив?

## 5. Целевая архитектура через полгода

Через полгода система «Александрит» должна выглядеть так:

### Observability
- Prometheus + Grafana для метрик всех сервисов, БД, RabbitMQ.
- Jaeger для distributed tracing — каждый заказ можно проследить от INITIATED до CLOSED.
- OpenSearch/ELK для централизованных логов с алертингом на аномалии.
- Дашборды для бизнеса: конверсия заказов, среднее время прохождения, процент «зависших».

### Надёжность доставки
- RabbitMQ с DLQ, publisher confirms, retry-политиками.
- Мониторинг очередей и алерты на рост DLQ.
- Минимум 2 ноды RabbitMQ в кластере.

### Производительность MES
- Redis-кеш для дашборда заказов с event-driven инвалидацией.
- Read-реплика MES DB для запросов дашборда.
- Расчёт стоимости вынесен в отдельный worker pool.

### API
- API Gateway перед MES API с rate limiting и квотами для B2B.
- Раздельный мониторинг B2B и B2C трафика.

### Инфраструктура
- Docker-контейнеры для всех приложений (подготовка к K8s).
- Kubernetes-кластер — в процессе миграции или уже мигрированы.
- Автоматизированные E2E-тесты для критических путей.
- CI/CD с автодеплоем в dev/release и manual gate в prod.

## 6. Топ-3 инициативы на ближайшие полгода

Если бы у меня была возможность выполнить только три инициативы:

### 1. Observability-стек (И1)

**Почему:** это фундамент. Без мониторинга, трейсинга и логов мы:
- Не можем доказать бизнесу, где именно теряются заказы.
- Не можем измерить эффект других улучшений.
- Реагируем на инциденты только по жалобам клиентов (реактивно, а не проактивно).

**Первый результат через 2-3 недели:** метрики RabbitMQ (DLQ, in-flight), базовые дашборды, трейсы для flow заказа.

### 2. Надёжная доставка RabbitMQ (И2)

**Почему:** это главная причина потери заказов. Каждый потерянный заказ — это потерянные деньги и репутация. После открытия API проблема усугубилась.

**Первый результат через 1-2 недели:** DLQ настроены, publisher confirms включены, есть retry-механизм. Сразу видим масштаб проблемы (сколько сообщений попадает в DLQ).

### 3. Кеширование MES + read-реплика (И3)

**Почему:** операторы — это «конвейер» компании. Если они не видят заказы вовремя, производство тормозит. Это напрямую влияет на throughput компании и удовлетворённость операторов (их вознаграждение зависит от скорости).

**Первый результат через 2-3 недели:** Redis-кеш для дашборда, read-реплика для MES DB.

### Ход рассуждений

Инициативы И1 и И2 решают главную боль бизнеса — потерю заказов и контрактов. И1 даёт видимость, И2 — устраняет (предполагаемую) корневую причину. И3 решает вторую по важности проблему — скорость производства. Вместе эти три инициативы закрывают наиболее болезненные бизнес-проблемы и создают базу для дальнейших улучшений.

Kubernetes (И4) и автоматизация CI/CD (И5) важны стратегически, но их отсутствие не вызывает немедленной потери денег. API Gateway (И6) тоже важен, но rate limiting можно реализовать проще (на уровне nginx — Л3) как временную меру.

## 7. Обоснование найма

Текущая команда (8 человек + архитектор): 2 Vue, 2 Java, 1 C#, 1 QA, 1 тимлид (C#), 1 PM, 1 DevOps. Для реализации плана команда перегружена в трёх узких местах:

### Кого нанять в первую очередь

**1. Второй DevOps / SRE-инженер (критично).**
- **Зачем:** на одном DevOps висит вся инфраструктура, CI/CD, observability и (в перспективе) миграция в K8s. И1, И4 и Л5 — всё упирается в него.
- **Когда:** прямо сейчас, до старта И1.
- **Альтернатива:** без найма И4 растянется на год+ и будет блокировать всё остальное.

**2. QA Automation Engineer (или развитие текущего QA).**
- **Зачем:** текущий QA хочет заниматься автоматизацией и уже делал прототипы. Нужно либо освободить его от ручного прогона E2E (наняв junior manual QA), либо нанять senior automation-инженера в пару.
- **Когда:** Q2, параллельно с запуском И5.
- **Обоснование:** без автотестов И4 (K8s) и любые крупные рефакторинги станут очень рискованными.

### Кого можно рассмотреть позже

**3. Backend-инженер (Java или C#) — по мере роста нагрузки.**
- **Зачем:** текущие 2 Java + 1 C# будут загружены эпиками (И2, И3, И6, И7). При параллельной работе над несколькими инициативами одного C#-разработчика на MES недостаточно.
