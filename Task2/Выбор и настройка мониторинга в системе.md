# Выбор и настройка мониторинга в системе

## 1. Мотивация

### Почему мониторинг необходим

Компания «Александрит» теряет клиентов и контракты из-за проблем с заказами. При этом у команды нет инструмента, чтобы:
- **Обнаруживать проблемы до жалоб клиентов.** Сейчас о сбоях узнают только от менеджеров по продажам, когда клиент уже недоволен.
- **Оценить масштаб проблем.** Сколько заказов реально теряется? Какой процент запросов завершается ошибкой? Как растёт нагрузка? Без данных ответов нет.
- **Принимать решения на основе фактов.** Бизнес хочет знать, нужны ли новые мощности, где узкое место. Яндекс Метрика покрывает только фронтенд магазина и не отражает B2B-нагрузку через API.

### Связь с проблемами из Task1

Мониторинг — фундамент для всей дорожной карты, намеченной в Task1:
- **P1 (потеря заказов):** мониторинг RabbitMQ (DLQ, in-flight, publish/consume rate) — единственный способ верифицировать гипотезу о потере сообщений между MES и CRM, на которой построен приоритет И2.
- **P2 (тормоза дашборда MES):** метрики latency, CPU, DB connections и размера таблиц нужны, чтобы локализовать bottleneck и измерить эффект И3 (кеширование + read-реплика).
- **P3 (SPOF):** метрики доступности инстансов обоснуют решение по И4 (миграция в K8s).
- **P4 (отсутствие observability):** текущее задание закрывает этот пункт напрямую.
- **P6 (медленные релизы):** метрики error rate после деплоя дадут объективную базу для решения о rollback.
- **P7 (нет SLA для B2B):** без per-client метрик (RPS, latency, errors по partner_id) ввести SLA невозможно.

### Что даст мониторинг компании

1. **Проактивное обнаружение инцидентов** — алерт придёт до жалобы клиента. Время реакции сократится с дней до минут.
2. **Понимание реальной нагрузки** — данные для планирования мощностей и обоснования найма.
3. **Измерение эффекта улучшений** — можно будет количественно оценить результат каждой инициативы (кеширование, DLQ и т.д.).
4. **SLA для B2B-партнёров** — метрики позволят определить и контролировать SLA для API.
5. **Снижение MTTR** (Mean Time To Recovery) — дашборды помогут быстрее локализовать проблему при инцидентах.

### Что НЕ покрывает это задание

Явно оставляем за рамками (но отмечаем как известный пробел):
- **Frontend RUM** (Core Web Vitals, JS-ошибки, клиентская latency). Сейчас частично покрыто Яндекс Метрикой для B2C-магазина, но для CRM и MES её нет. Рекомендуется отдельной инициативой внедрить Sentry или self-hosted RUM.
- **Централизованное логирование** — это отдельная инициатива (ELK/OpenSearch), здесь обсуждаем только метрики.
- **Distributed tracing** (Jaeger/Tempo) — также отдельная инициатива, хотя идеально внедрять вместе с метриками.

## 2. Выбор подхода к мониторингу

Для разных частей системы используются разные подходы:

### API-сервисы (Shop API, CRM API, MES API) — метод RED

**RED** (Rate, Errors, Duration) оптимален для request-driven сервисов:
- **Rate** — количество запросов в секунду. Показывает нагрузку и позволяет отслеживать аномалии.
- **Errors** — количество и процент ошибок. Прямой индикатор здоровья сервиса.
- **Duration** — латентность запросов. Деградация latency — ранний сигнал о проблемах.

### Инфраструктура (EC2, БД, S3) — метод USE

**USE** (Utilization, Saturation, Errors) оптимален для ресурсов:
- **Utilization** — какой процент ресурса используется (CPU, память, диск, соединения).
- **Saturation** — есть ли очередь ожидания (запросы к БД в очереди, thread pool заполнен).
- **Errors** — ошибки на уровне ресурса (OOM, disk full, connection refused).

### RabbitMQ — «Четыре золотых сигнала»

Для брокера сообщений важны все четыре сигнала:
- **Latency** — задержка обработки сообщений.
- **Traffic** — скорость публикации и потребления сообщений.
- **Errors** — сообщения в DLQ, nack-и, ошибки соединения.
- **Saturation** — глубина очередей, использование памяти брокера.

## 3. Метрики для отслеживания

### 3.1. RabbitMQ

| # | Метрика | Зачем | Ярлыки (labels) |
|---|---------|-------|-----------------|
| 1 | **Number of dead-letter-exchange letters** | Критически важная метрика. DLQ — это «потерянные» сообщения, которые не были обработаны. Рост DLQ = заказы теряются. Алерт при > 0. | `queue` (имя исходной очереди), `reason` (expired/rejected/maxlen) |

| # | Метрика | Зачем | Ярлыки |
|---|---------|-------|--------|

### 3.2. API-сервисы — Rate

| # | Метрика | Зачем | Ярлыки |
|---|---------|-------|--------|
| 3 | **RPS for Shop API** | Базовая нагрузка на магазин. Нужна для capacity planning и обнаружения аномалий. | `method`, `endpoint`, `status_code` |

> ⚠️ **Осторожно с cardinality.** Label `user_id` для Shop API создаст очень высокую cardinality в Prometheus (каждый пользователь = новая time series), что «взорвёт» хранилище. Правильный подход:
> - Для B2C Shop API: **не использовать `user_id` как label** в Prometheus. Вместо этого экспортировать агрегированные top-N пользователей (через recording rules) или отслеживать аномалии через логи/ClickHouse.
> - Для B2B MES API: `partner_id` допустим — число B2B-партнёров невелико и контролируемо.
> - Общее правило: в Prometheus-лейблы идёт только **ограниченное и предсказуемое** множество значений.

## 4. План действий

### Этап 1: Инфраструктура мониторинга (1-2 недели)

1. Развернуть Prometheus-инстанс в Yandex Cloud (Managed Prometheus или на выделенном EC2).
2. Развернуть Grafana для визуализации.
3. Настроить node_exporter на всех EC2-инстансах (CPU, memory, disk, network).
4. Подключить postgres_exporter к Shop DB и MES DB.
5. Подключить rabbitmq_exporter к RabbitMQ.
6. Настроить retention policy: 30 дней для полного разрешения, 1 год для агрегатов.

### Этап 2: Метрики приложений (2-3 недели)

7. Добавить Prometheus-клиенты в Shop API и CRM API (Java — micrometer/prometheus).
8. Добавить Prometheus-клиент в MES API (C# — prometheus-net).
9. Инструментировать все HTTP-эндпоинты (request count, latency histogram, error count).
10. Добавить бизнес-метрики: счётчики заказов по статусам, время расчёта стоимости.

### Этап 3: Дашборды и алертинг (1-2 недели)

11. Создать дашборд «Инфраструктура» в Grafana (CPU, memory, disk, DB connections).
12. Создать дашборд «API Health» (RPS, latency, errors по каждому сервису).
13. Создать дашборд «RabbitMQ» (queue depth, DLQ, publish/consume rate).
14. Создать дашборд «Бизнес» (заказы по статусам, зависшие заказы, время расчёта).
15. Настроить Alertmanager с каналами уведомлений (Telegram/Slack/email).
16. Настроить алерты (см. раздел «Насыщенность» ниже).

### Этап 4: Итерация (ongoing)

17. Ревью метрик и дашбордов с командой — убрать ненужное, добавить недостающее.
18. Интеграция с on-call процессом.

## 5. Показатели насыщенности и пороговые значения (дополнительное задание)

### 5.1. Что такое «насыщенность» в USE-методе

В методе USE **Saturation** — это не «процент использования ресурса» (это Utilization), а **объём работы, которую ресурс не успевает обслуживать** — очередь запросов, ожидающих освобождения ресурса. Это более ранний и точный сигнал проблемы, чем Utilization:
- CPU на 100% утилизации может быть нормой (загруженный воркер), а вот рост runqueue — всегда деградация.
- Memory на 90% занято буферами — ОК, а вот использование swap — тревожный сигнал.
- БД может иметь 50% CPU, но если клиенты ждут соединения в очереди — это узкое место.

### 5.2. Выбранные показатели насыщенности

| # | Ресурс | Показатель насыщенности | Почему именно этот | Источник данных |
|---|--------|-------------------------|--------------------|-----------------|
| S1 | CPU EC2 | **Run queue length** (`node_load1` / vCPU) | Рост очереди процессов > число vCPU означает, что задачи ждут CPU. Более точный сигнал деградации, чем CPU %. | node_exporter |
| S2 | Memory EC2 | **Swap used bytes + page swap-in rate** | Использование swap на EC2 почти всегда = деградация производительности. Normal value = 0. | node_exporter |
| S3 | Disk I/O | **Disk I/O wait time** (`node_disk_io_time_weighted`) и **iowait %** | Показывает, что процессы ждут дисковые операции. Критично для БД. | node_exporter |
| S4 | Shop DB / MES DB | **Pending connections** (`pg_stat_activity` в состоянии `waiting`) и **connection wait time** | Прямой индикатор исчерпания пула соединений — клиенты ждут, а не отбрасываются. | postgres_exporter |
| S5 | Shop DB / MES DB | **Replication lag** (после внедрения реплик) | Когда появится read-реплика для MES DB (И3), отставание реплики = деградация чтения дашборда. | postgres_exporter |
| S6 | RabbitMQ | **Queue depth** (`rabbitmq_queue_messages_ready`) | Прямой показатель: сообщения накапливаются, потребитель не справляется. | rabbitmq_exporter |
| S7 | RabbitMQ | **Unacked messages** (in-flight) | Рост означает зависшего потребителя. Ранний сигнал до роста queue depth. | rabbitmq_exporter |
| S8 | RabbitMQ | **DLQ count** | Каждое сообщение — потенциально потерянный заказ. Zero-tolerance. | rabbitmq_exporter |
| S9 | Java-приложения (Shop/CRM API) | **Thread pool queue size** (Tomcat/Jetty) | Запросы ждут свободный worker thread — ранний сигнал нехватки мощности, до роста latency. | micrometer |
| S10 | JVM (Shop/CRM API) | **GC pause time** и **GC frequency** | Длинные GC паузы = saturation по memory allocation rate. | micrometer |
| S11 | Бизнес-уровень | **Количество заказов в нетерминальном статусе дольше SLA** | Бизнес-метрика saturation: система «копит» необработанные заказы. | custom exporter из БД |

| PRICE_CALCULATED → MANUFACTURING_APPROVED | 24 ч | > 24 ч | > 48 ч | Slack менеджеру, проверка очереди на подтверждение |
| MANUFACTURING_APPROVED → MANUFACTURING_STARTED | 48 ч | > 48 ч | > 120 ч | Проверка доступности операторов |
| MANUFACTURING_STARTED → MANUFACTURING_COMPLETED | 14 дней | > 14 дней | > 21 день | Эскалация на руководителя производства |
| MANUFACTURING_COMPLETED → PACKAGING | 24 ч | > 24 ч | > 48 ч | Slack операторам |
| PACKAGING → SHIPPED | 24 ч | > 24 ч | > 48 ч | Проверка логистики |
| SHIPPED → CLOSED | 14 дней | > 14 дней | > 30 дней | Проверка интеграции с транспортной компанией |

### 5.4. Обоснование порогов

- **CPU 70%/90%:** оставляем запас для пиков. При 70% ещё есть время отреагировать. При 90% — деградация неизбежна.
- **Runqueue/vCPU > 1.5:** значит в среднем 1.5 задачи на ядро ждут выполнения — начало деградации. > 3 — сервис ощутимо тормозит.
- **Memory 80%/95%:** Java-приложения активно используют heap. 80% нормально для JVM, но сигнал проверить. 95% — близко к OOM.
- **Swap > 0 на EC2:** инстанс не рассчитан на использование swap; любое использование = проблема.
- **DB connections 80%/95%:** PostgreSQL по умолчанию имеет max_connections=100. С двумя клиентами (Shop API + CRM API) на Shop DB исчерпание реально.
- **DB pending connections > 5:** даже 5 ожидающих клиентов = пул исчерпан, запросы встают в очередь.
- **DLQ > 0:** каждое сообщение в DLQ — потенциально потерянный заказ. Zero-tolerance.
- **Thread pool queue > 10:** при нормальной работе очередь должна быть близка к нулю; рост = нехватка workers.
- **GC pause p99 > 500 мс:** долгие паузы напрямую отражаются на latency API.
- **SLA по статусам:** пороги выбраны из обещанного клиентам срока «3 недели» от заказа до отгрузки. Раскладка по переходам консервативна — алерт срабатывает раньше, чем клиент потеряет терпение.
